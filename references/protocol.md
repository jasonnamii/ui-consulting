# ux-advisor 프로토콜 (실행 규정)

## 📥 입력 파싱

### Step 1: 도메인 감지
질문에서 다음 신호 추출:
- **도메인**: 모바일/웹/이커머스/핀테크/헬스/교육/소셜/AI/B2B/게임
- **타겟**: 노년/Gen Z/파워유저/대중/아동/미지정
- **컨텍스트**: 이동/업무/여가/긴급/미지정
- **제약**: 규제/리소스/기존 유저베이스/리스크 선호도

→ `references/domain-lens.md` 참조하여 렌즈 적용

### Step 2: 질문 유형 분류

| 유형 | 예시 | 대응 |
|------|------|------|
| 패턴 질문 | "온보딩 어떻게?" "결제 UX는?" | 4단계 스펙트럼 기본 |
| 비교 질문 | "A vs B 어떤 게 좋아?" | 각 옵션을 스펙트럼에 위치 |
| 진단 질문 | "이거 문제 있나?" | 이론 위반 진단 + 개선 스펙트럼 |
| 전략 질문 | "차별화 포인트?" | 🟨~🟥 집중, 🟦🟩은 반면교사 |
| 구현 질문 | "이 버튼 어디 둘까?" | Fitts/Thumb Zone 직답, 스펙트럼 생략 가능 |

## 🔗 후속 스킬 연계

### 사용자가 단계 선택 후
1. **"이거로 갈래"** → 선택 확인 + 다음 단계 제안
2. **"UI 설계해줘"** → `ui-action-designer` 스킬 호출 (Action→Task→SHE)
3. **"바로 디자인"** → `design-skill` 호출 (HTML/MD 시각화)
4. **"더 깊게 알고 싶어"** → 해당 단계 심화 (이론 추가·사례 확장)
5. **"다른 질문"** → 새 루프

### 자동 연계 판정 불가 시
선택 게이트: "🎯 어떻게 진행할까요? ①이 방향 확정 ②다른 단계 심화 ③UI 설계 착수 ④바로 시각화"

## 🎯 통찰력 확보 규칙 (품질 보증)

### 반드시 포함
- **비유 1개 이상** — 각 단계. "이건 X와 같다" 단순 비유 금지. 그림이 그려지는 비유.
- **실제 서비스명 2~3개** — "어떤 앱"이 아니라 "Toss"·"Slack" 구체명
- **이론 근거** — NN 휴리스틱 번호·법칙명 명시

### 반드시 피함
- 추상적 원칙만 나열 ("사용자 중심이어야 합니다" 같은 공허한 말)
- 이론 없는 의견
- 사례 없는 이론
- 비유 없는 사례

### 품질 체크리스트 (자가점검)
- [ ] 각 단계에 비유 있나?
- [ ] 각 단계에 실제 서비스명 있나?
- [ ] 이론-사례-비유 3요소 연결되나?
- [ ] 4단계가 실제로 다른가? (중복 아닌가)
- [ ] 사용자가 선택할 수 있게 차이가 명확한가?

## 🚨 예외 처리

### 리서치 필요한 경우
- 최신 사례(2024+ 신규 서비스) 요청 시
- 매우 니치한 도메인 (의료기기 UX 등)
→ `research-frame` LIGHT 모드 발동 (폭 유지·깊이 최소)

### 사용자 심리 분석 필요
→ `human-skill` 호출 + 결과를 스펙트럼에 반영

### 임팩트 증폭 (혁명 답변 강화)
→ `hit-skill` 연계 (3층 아키텍처 적용)

### 모순 해결 (혁명 답변에서 트레이드오프)
→ `triz` 연계 (40 발명원리 적용)

## 🪤 Gotchas

| 함정 | 대응 |
|------|------|
| 4단계가 다 비슷하게 보임 | 축=관행 이탈도 상기, 시대감각 강조 |
| 사용자가 "정답"을 요구 | "정답 없음, 4단계 각각의 맥락" 설명 |
| 혁명만 매력적으로 보이게 제시 | 🟥 답변에 실패 사례·리스크 반드시 병기 |
| 너무 긴 답변 | 축약 포맷 전환 |
| 특정 사례 반복 | 도메인 다양성 확보, `research-2-cases.md` 넓게 활용 |
